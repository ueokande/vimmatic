# AGENTS.md

Guidance for CLI coding agents working in the **vimmatic** repository — a
Vim-like keybinding browser extension (WebExtension) for Firefox and Chrome.

## Project overview

- Language: TypeScript (strict), React 19 for UI surfaces (console, options
  page).
- Package manager: **pnpm** (`packageManager: pnpm@11.25.0` in
  `package.json`). Do not use npm/yarn.
- Node version: see `engines.node` in `package.json`.
- Build tool: Vite (`script/build.mjs`), producing `dist/firefox` and
  `dist/chrome`.
- Architecture follows a layered/clean-architecture style per WebExtension
  context (`background`, `content`, `console`, `options`):
  - `controllers` — entry points reacting to messages/events.
  - `usecases` — application logic.
  - `repositories` — persistence/storage access (chrome.storage, etc.).
  - `presenters` / `clients` — outbound communication to other
    contexts/frames.
  - `messaging` — cross-context message passing (background ⇄ content ⇄
    console).
  - `di.ts` — Inversify dependency-injection container setup per context.
  - `domains` / `hint` / `operators` / `command` / `property` — domain
    models and feature-specific logic.
- `src/shared` holds code shared across all contexts (settings schema,
  keymaps, blacklist, search engines, styles, etc.).
- `src/settings` defines the user-facing settings schema/serialization
  (`schema.ts`, `serdes.ts`, `default.ts`).
- Tests mirror `src/` under `test/` (unit tests, Vitest) and `e2e/`
  (Playwright, real browser).

## Common commands

Run from the repo root.

```bash
pnpm install --frozen-lockfile   # install dependencies (matches CI)
pnpm start                       # dev build with watch (nodemon + vite)
pnpm build                       # production build into ./dist
pnpm package                     # build + zip extension packages
pnpm type-checks                 # tsc --noEmit
pnpm lint                        # biome ci . (check only)
pnpm lint:fix                    # biome check --write . (auto-fix)
pnpm test                        # vitest unit tests
pnpm test:e2e                    # playwright e2e tests (firefox, see below)
```

CI (`.github/workflows/build.yml`) runs, in order:
`pnpm install --frozen-lockfile` → `pnpm type-checks` → `pnpm lint` →
`pnpm test` → `pnpm package`, plus a separate e2e job. Match this sequence
before considering a change complete.

### Running a subset of tests

```bash
pnpm vitest run test/background/...        # single unit test file/dir
pnpm exec playwright test --browser=firefox ./e2e/find.test.ts
```

E2E tests require Firefox via Playwright (`pnpm exec playwright install
firefox`) and a built extension (`pnpm build`); CI mixes in the addon with
`webext-agent`. E2E is heavier — prefer unit tests for routine changes.

## Linting & formatting

- Formatter/linter: **Biome** (`biome.json`), not ESLint/Prettier.
- Key enforced rules: double quotes, 2-space indent, 80-col width, no default
  exports (except `vitest.config.ts`), separated `import type`, no
  `console.*` (except in `script/**/*.mjs`), organize-imports on save.
- Run `pnpm lint:fix` before finishing a change; `pnpm lint` must pass
  (CI uses `biome ci .`, which fails on any needed formatting/lint fix).

## TypeScript conventions

- Dependency injection via `inversify` + `@inversifyjs/binding-decorators`:
  classes are decorated with `@injectable()` and consumers use
  `@inject(SomeClass)` in constructors (see `src/background/Application.ts`).
  Each context has its own `di.ts` wiring container bindings.
- Validation/schemas use `zod` (see `src/settings/schema.ts`,
  `src/shared/*`).
- Keep new code within the existing per-context layering (controller →
  usecase → repository/client) instead of calling `chrome.*` APIs directly
  from UI or usecase code when a repository/client abstraction already
  exists for that concern.

## Comments & commit messages

- Code comments: explain **why not** — i.e. why the obvious/simpler
  alternative wasn't used, or a non-obvious constraint/trade-off — not what
  the code does or why the chosen approach works. Don't restate the code in
  prose; skip comments that are redundant with self-explanatory code.
- Commit messages: explain **why** — the motivation/reasoning behind the
  change (bug being fixed, requirement driving it, trade-off chosen). Avoid
  messages that only restate what changed; that's already visible in the
  diff.

## Documentation

- User-facing docs live in `docs/` (Jekyll site, deployed via
  `.github/workflows/gh-pages.yml` to https://ueokande.github.io/vimmatic/).
  Update the relevant page (`docs/keymaps.md`, `docs/console_commands.md`,
  `docs/properties.md`, `docs/search_engines.md`, `docs/blacklist.md`,
  `docs/styles.md`) when changing user-visible keymaps, commands, settings
  properties, or styling options.
- `CHANGELOG.md` is generated by release-please; do not hand-edit release
  entries.

## Things to double-check before finishing

1. `pnpm type-checks`, `pnpm lint`, and `pnpm test` all pass.
2. If behavior affecting keymaps/commands/settings changed, the matching
   `docs/*.md` page was updated.
3. New source files follow the existing per-context folder structure
   (controllers/usecases/repositories/etc.) rather than introducing ad-hoc
   patterns.
4. Avoid editing generated/output directories: `dist/`, `node_modules/`,
   `pnpm-lock.yaml` (unless intentionally updating a dependency).
